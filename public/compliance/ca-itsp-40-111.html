§1 IntroductionExplains the publication's purpose: guiding practitioners on approved cryptography for sensitive government information up to Protected B.
§1.1 Practitioner notesDeprecated algorithms are barred from new systems and should be replaced; pick primitives and parameters from the recommended lists. Coming soon
§1.2 Policy driversGovernment departments must put security policies and procedures in place under the federal security policy. Coming soon
§1.3 Relationship to the IT risk management processDescribes how departmental and system-level risk management activities fit together in a continuous cycle. Coming soon
§2 Post quantum cryptographyIntroduces NIST's quantum-resistant key establishment and signature standards that will gradually replace classical public-key schemes. Coming soon
§3 Encryption algorithmsIntroduces the encryption algorithms approved for protecting confidentiality of information up to Protected B.
§3.1 Advanced Encryption Standard algorithmAES is the recommended cipher, using 128, 192 or 256-bit keys. Coming soon
§4 Encryption algorithm modes of operationIntroduces the block cipher modes recommended for use with AES.
§4.1 Protecting the confidentiality of informationLists confidentiality-only AES modes; ECB unsuitable for bulk data, CBC needs padding, IVs and counters must be handled properly. Coming soon
§4.2 Protecting the confidentiality and authenticity of informationAuthenticated encryption should use CCM or GCM to protect both secrecy and integrity. Coming soon
§5 Key establishment schemesIntroduces approved schemes for creating shared secret keys between parties.
§5.1 Rivest-Shamir-AdlemanRSA key establishment needs a modulus of 2048 bits or more, 3072 by 2030, retire by 2035. Coming soon
§5.2 Finite Field Cryptography Diffie-Hellman and Menezes-Qu-VanstoneFinite-field Diffie-Hellman and MQV need primes of 2048 bits or more, 3072 by 2030, phase out by 2035. Coming soon
§5.3 Elliptic curve cryptography Cofactor Diffie-Hellman and Menezes-Qu-VanstoneElliptic-curve Diffie-Hellman and MQV allowed on P-256, P-384, P-521; P-224 and binary curves end by 2030. Coming soon
§5.4 Module-Lattice-Based Key-Encapsulation MechanismML-KEM is the recommended quantum-resistant key establishment, in 512, 768 or 1024 parameter sets. Coming soon
§6 Digital signature schemesIntroduces approved digital signature schemes for integrity and origin authentication, noting one scheme to retire by 2030.
§6.1 Rivest-Shamir-AdlemanRSA signatures (PKCS1 v1.5 or PSS) need 2048-bit moduli or more, 3072 by 2030, retire by 2035. Coming soon
§6.2 Digital Signature AlgorithmDSA is deprecated for new applications; existing uses need 2048-bit fields and removal by 2030. Coming soon
§6.3 Elliptic Curve Digital Signature AlgorithmECDSA is recommended on P-256, P-384, P-521; P-224 and binary curves end by 2030, ECDSA by 2035. Coming soon
§6.4 Edwards-Curve Digital Signature AlgorithmEdDSA is recommended with Edwards25519 or Edwards448, not the prehash variant, and retires by 2035. Coming soon
§6.5 Module-Lattice-Based Digital Signature AlgorithmML-DSA is the recommended general-purpose quantum-resistant signature, with three parameter sets. Coming soon
§6.6 Stateless Hash-Based Digital Signature AlgorithmSLH-DSA is recommended as a stateless hash-based quantum-resistant signature, with listed SHA2 and SHAKE parameter sets. Coming soon
§6.7 Stateful hash-based signature schemesStateful hash-based signatures remain usable only if signer can safely protect and manage private key state. Coming soon
§7 Hash functionsIntroduces hash functions approved for use with the publication's algorithms.
§7.1 Secure Hash Algorithm-1SHA-1 must not be used for signatures or collision resistance, and is being retired elsewhere. Coming soon
§7.2 Secure Hash Algorithm-2SHA-2 family functions are recommended for signatures, MACs, KDFs and RBGs; SHA-224 ends by 2030. Coming soon
§7.3 Secure Hash Alogorithm-3SHA-3 family functions are recommended for signatures, MACs, KDFs and RBGs; SHA3-224 ends by 2030. Coming soon
§8 Extendable output functionsIntroduces the two extendable-output functions approved for selected algorithms.
§8.1 SHAKESHAKE128 and SHAKE256 are recommended only inside the listed key establishment, signature and KMAC uses. Coming soon
§9 Message authentication codesIntroduces message authentication codes recommended for integrity and origin authentication.
§9.1 Keyed-Hash Message Authentication CodeHMAC is recommended with keys of at least 112 bits, rising to 128 by 2030. Coming soon
§9.2 Cipher-based Message Authentication CodeCMAC is recommended, but only when built on AES. Coming soon
§9.3 Galois/Counter Mode Message Authentication CodeGMAC is recommended, but only when built on AES. Coming soon
§9.4 KECCAK Message Authentication CodeKMAC128 and KMAC256 are recommended with keys of 112 bits or more, 128 by 2030. Coming soon
§10 Key derivation functionsIntroduces key derivation functions for turning shared or pre-shared secrets into strong keys.
§10.1 One-Step Key Derivation FunctionThe one-step key derivation method from NIST SP 800-56C is recommended. Coming soon
§10.2 Two-Step Key Derivation FunctionThe extract-then-expand derivation method is recommended; TLS 1.3's HKDF follows it. Coming soon
§10.3 Key derivation using pseudorandom functionsKey derivation built on pseudorandom functions per NIST SP 800-108 is recommended. Coming soon
§10.4 Internet Key Exchange version 2 Key Derivation FunctionWithin IKEv2, use the IKEv2 key derivation function from SP 800-135. Coming soon
§10.5 Transport Layer Security version 1.2 Key Derivation FunctionWithin TLS 1.2, use the protocol's key derivation function from SP 800-135. Coming soon
§10.6 Secure Shell Key Derivation FunctionWithin SSH, use the SSH key derivation function from SP 800-135. Coming soon
§10.7 Secure Real-time Transport Protocol Key Derivation FunctionWithin SRTP, use the SRTP key derivation function from SP 800-135. Coming soon
§10.8 Trusted Platform Module Key Derivation FunctionWithin TPM sessions, use the TPM key derivation function from SP 800-135. Coming soon
§10.9 Password-based Key Derivation FunctionFor stored data, derive keys from passwords of at least twelve characters using the NIST SP 800-132 method. Coming soon
§11 Key wrap modes of operationIntroduces key wrapping modes protecting confidentiality and integrity of cryptographic keys.
§11.1 Advanced Encryption Standard Key WrapUse AES Key Wrap when input is always a multiple of 64 bits. Coming soon
§11.2 Advanced Encryption Standard Key Wrap with PaddingUse AES Key Wrap with Padding when input length is not a multiple of 64 bits. Coming soon
§12 Random bit generatorsRandom bits should come from NIST-specified constructions using Hash, HMAC or CTR DRBGs seeded with at least 112 bits of entropy. Coming soon
§13 Commercial technologies assurance programsRecommends validated implementations and modules (CAVP, CMVP, FIPS 140-3, Common Criteria) operated in approved modes. Coming soon
§14 SummarySummarises that cryptography protects sensitive information and algorithms must be chosen and implemented to meet requirements. Coming soon
