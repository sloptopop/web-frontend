A to Z

Every transformation, step by step

sloptopop changes code the same way every time: find the problem, understand what the code does, plan the fix in small checkable steps, change only those bytes, prove each change, and hand you a branch to review. Here is the whole path, from the repository you start with to what you get back.

A committed environment file

Available now · real output of sloptopop 0.1.0

This is what sloptopop does today, run on a small demo repository. Every output below is what the engine printed.

  1. A The repository

    A small project with an environment file committed by mistake. The key is a placeholder; a real one would be reported the same way.

    demo/
├── .env
│     STRIPE_KEY=sk_live_EXAMPLE_not_a_real_key
│     DATABASE_URL=postgres://localhost/shop
└── src/pay.ts

  2. B Detect

    sloptopop check reports four findings. The one that matters here, exactly as the engine prints it:

    $ sloptopop check . --format json
{
  "rule": "secrets.committed",
  "severity": "error",
  "path": ".env",
  "line": 1,
  "message": "Environment file with values is in the repository",
  "fix": {
    "kind": "createFile",
    "path": ".gitignore",
    "template": "gitignore"
  },
  "remediation": "Rotate every credential in the file, remove the file from the repository and its history, and add `.env*` to `.gitignore`; keep a `.env.example` without values."
}

also found: ci.missing, hook.missing, licence.missing

  3. C Plan

    A dry run lists every change before anything is written. Only mechanical fixes are planned; nothing existing is ever overwritten.

    $ sloptopop fix .
"changes": [
  { "path": ".githooks/pre-push",         "template": "pre-push",      "status": "planned" },
  { "path": ".github/workflows/gate.yml", "template": "gate-workflow", "status": "planned" },
  { "path": ".gitignore",                 "template": "gitignore",     "status": "planned" }
]

  4. D Apply

    With --apply the same three files are created. The new .gitignore keeps environment files out of the repository from now on:

    $ sloptopop fix . --apply
.gitignore  created

# Local environment files hold secrets; keep a .env.example without values.
.env
.env.*
!.env.example

  5. E Check again

    Three of the four findings are gone. The licence is left on purpose: choosing a licence is your decision, so sloptopop gives guidance and no fix.

    $ sloptopop check .
licence.missing  error  LICENSE  No licence file at the repository root

  6. F What stays with you

    The key was already committed, so ignoring the file now does not make it safe. Rotate it at the provider and remove the file from the history. sloptopop never rewrites history, never calls a provider and never pushes.

An API key written into the code

In development · designed behaviour, not yet available

The next transformation moves the key out of the code without changing what the code does, and proves it at every step. This walkthrough shows how it is designed to work.

  1. A The code

    An API key written straight into the source, the most common way AI-written code leaks one.

    // src/pay.ts
import Stripe from "stripe";

const stripe = new Stripe("sk_live_EXAMPLE_not_a_real_key");

export async function pay(amount: number) {
  return stripe.charges.create({ amount, currency: "eur" });
}

  2. B Detect

    The Detector reports the literal and where it is. The key's value is never printed or stored.

    secrets.committed  error  src/pay.ts:3  Stripe secret key in source

  3. C Understand what the code does

    Before changing anything, sloptopop models what the code does for the business: this literal fills the credential of an outbound call to Stripe from pay(). The secret is reduced to its class.

    value   val:literal:sym:shop-api::stripe.:credential
        source literal · redacted · class secret.stripe
effect  fx:net.out:api.stripe.com
edge    configures  value → effect  slot credential
edge    performs    sym:shop-api::pay().  → effect

  4. D Plan, broken into checkable steps

    The fix is split until every step is one operation from a fixed menu. Step A keeps behaviour identical; Step B changes it and ships separately; rotating the key is a task for a person.

    Problem: no secret in source, payments behave the same
├─ Step A  move the value to configuration
│   ├─ ADD_CONFIG_KEY               STRIPE_KEY
│   ├─ REPLACE_LITERAL_WITH_CONFIG  src/pay.ts:3   (used once, not in a test)
│   └─ ADD_ENV_EXAMPLE_KEY          STRIPE_KEY=    (no value)
├─ Step B  refuse to start when STRIPE_KEY is missing   (separate commit)
└─ Manual  rotate the key at Stripe, set it in every environment, revoke the old one

  5. E Change only those bytes

    Each operation becomes a byte-exact edit that checks the old text first. Nothing else in the file is touched or reformatted.

      --- a/src/pay.ts  +++ b/src/pay.ts  import Stripe from "stripe";+ import { config } from "./config";  - const stripe = new Stripe("sk_live_EXAMPLE_not_a_real_key");+ const stripe = new Stripe(config.STRIPE_KEY);  --- a/.env.example  +++ b/.env.example+ STRIPE_KEY=

  6. F Prove it

    Every edit is checked before it is kept. Any check that cannot decide stops the change and asks a person instead of guessing.

    ✓ bytes outside the edits are identical
✓ every touched file still parses
✓ the model changed exactly as planned: the credential now comes from config, nothing else moved
✓ the type checker reports no new errors
✓ the tests that run the edited line pass
✓ a fresh scan no longer finds the key, and finds nothing new

  7. G Hand over

    You get a branch to review, never a merge.

    branch  sloptopop/externalize-stripe-key
  commit 1  Step A: read STRIPE_KEY from config (behaviour unchanged)
  commit 2  Step B: fail fast when STRIPE_KEY is missing
checklist
  [ ] rotate the key at Stripe
  [ ] set STRIPE_KEY in every environment
  [ ] revoke the old key
  [ ] remove it from the git history
