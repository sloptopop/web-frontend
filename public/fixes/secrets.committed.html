Issue type · error

secrets.committed

What it means. Secret material is in a tracked file. The Detector recognises private-key headers, tokens with a fixed provider prefix and exact length (AWS, GitHub, GitLab, Slack, Stripe live keys, Google API, npm), and committed .env files with values that the root .gitignore does not ignore. Secret scanners such as gitleaks, run by sloptopop collect, report here too.

Why it matters. Anyone with read access to the repository, a fork or a clone has the credential. Removing the line later does not revoke it.

What to do. 1. Treat the credential as compromised: rotate it at the provider and revoke the old one. 2. Load it from the environment or a secret manager instead of the source. 3. Remove it from the repository and its history (for example with git filter-repo), and from forks. 4. For .env files: untrack the file, add .env* to .gitignore, and keep a .env.example with keys but no values.

Automatic fix. fix creates a .gitignore when an environment file is the problem and there is none. Transformation: a secret literal in JavaScript or TypeScript becomes an environment read (secrets → env reads). Coming: secrets in env files. Rotation always stays a manual task.

Real fixes, by language

Each one is an edit sloptopop applied to a public repository, checked by the Guider, linked to the file at the commit it was made on. Committed secret values are shortened, never republished.
