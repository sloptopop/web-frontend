Slop to pop

Anti-patterns, turned into design patterns

sloptopop finds code written in a known anti-pattern and rewrites it into the design pattern that fixes it, the same way every time, with no AI model choosing the change. These conversions work today in sloptopop's development build and are not in a release yet. Each example below is real output: the rule found the anti-pattern in a test program written for that pattern, sloptopop rewrote it, and both versions were run and compared.

On real open-source code sloptopop still declines most sites it finds. It converts only when it can prove every fact the conversion depends on; when it can't, it reports which fact is missing instead of guessing.

  1. Singleton, from a new client on every call
  2. Dependency injection, from reaching for a global
  3. Builder, from a long positional constructor
  4. Factory, from the same creation choice, copied
  5. Strategy, from the same switch, repeated
  6. Facade, from reaching into a module's internals

Singleton

Works in the development build · Go

Slop: A new client on every call (rule design.client-per-call). Pop: Singleton.

handle() built a new http.Client on every call, so no connection was ever reused. sloptopop moves it into one shared client, created once on first use with sync.OnceValue. It does this only for client types its library registry lists as safe to share across calls; where it can't show that, for example when a shared client would also share cookies, it leaves the code alone and says which fact is missing.

  api.go  package main    import "net/http"+ import "sync"    var transport = &http.Transport{}  + var sharedC = sync.OnceValue(func() *http.Client {+ 	return &http.Client{Transport: transport}+ })+   func handle() string {- 	c := &http.Client{Transport: transport}+ 	c := sharedC()  	answer, err := c.Get("http://127.0.0.1:9/")  	if err != nil {  		return "refused"

Evidence: on each of its 2 test inputs the program gave the same output, exit code, exceptions and files before and after; a fresh scan no longer finds the anti-pattern; the comparison caught each of the four changes planted to test it; and two runs gave identical results.

Converts the same way in: C#, C++, Go, Java, JavaScript, Kotlin, Python, Rust, Swift, TypeScript.

Dependency injection

Works in the development build · Java

Slop: Reaching for a global (rule design.global-accessor). Pop: Dependency injection.

countOrders fetched its database from a global registry, so a caller or a test could not hand it a different one. sloptopop adds an overload that takes the database as a parameter, and the original signature calls it with the global, so every existing caller keeps working unchanged.

  Orders.java  final class Orders {      static String countOrders(int user) {-         Db db = Registry.currentDb();+         return countOrders(user, Registry.currentDb());+     }+ +     static String countOrders(int user, Db db) {          return db.describe(user);      }  }

Evidence: on each of its 5 test inputs the program gave the same output, exit code, exceptions and files before and after; a fresh scan no longer finds the anti-pattern; the comparison caught each of the four changes planted to test it; and two runs gave identical results.

Converts the same way in: C#, C++, Go, Java, JavaScript, Kotlin, PHP, Python, Rust, Swift, TypeScript.

Builder

Works in the development build · Kotlin

Slop: A long positional constructor (rule design.long-constructor). Pop: Builder.

Order takes six or seven arguments in a row, four of them numbers, so swapping two compiles and runs silently wrong. Kotlin's own answer to a builder is named arguments, so sloptopop names every argument at every call. The values and their order stay exactly as they were.

Evidence: on each of its 3 test inputs the program gave the same output, exit code, exceptions and files before and after; a fresh scan no longer finds the anti-pattern; the comparison caught each of the four changes planted to test it; and two runs gave identical results.

Factory

Works in the development build · Rust

Slop: The same creation choice, copied (rule design.repeated-creation). Pop: Factory.

ship and reship made the same choice between FastSink and SlowSink, written out twice. sloptopop moves the choice into one creation function, create_sink, and calls it from both places, so the next kind of sink is added once.

Evidence: on each of its 4 test inputs the program gave the same output, exit code, exceptions and files before and after; a fresh scan no longer finds the anti-pattern; the comparison caught each of the four changes planted to test it; and two runs gave identical results.

Strategy

Works in the development build · Python

Slop: The same switch, repeated (rule design.repeated-switch). Pop: Strategy.

Facade

Works in the development build · TypeScript

Slop: Reaching into a module's internals (rule arch.module-internals-access). Pop: Facade.

The reports module imported price straight from a file inside the orders module. The orders module already exports price from its public entry point, so sloptopop points the import there, and orders can reorganise its internals without breaking reports.

  reports/job.ts- import { price } from "../orders/internal/price";+ import { price } from "../orders/index";    orders/index.ts (unchanged)  // Synthetic program (APC-6), generic names.  export { price } from "./internal/price";

Evidence: on each of its 4 test inputs the program gave the same output, exit code, exceptions and files before and after; a fresh scan no longer finds the anti-pattern; the comparison caught each of the four changes planted to test it; and two runs gave identical results.
